# Linux packaging

Every Linux asset of a release is made from one payload folder, which `native/packaging/build/linux.sh` builds. Each script below takes what it says and fails with one sentence naming what is missing. The images and downloaded tools they run are pinned in `pins.sh`, and the layout they share (the payload folder in `/usr/lib/mcbench-lite`, the `/usr/bin` symlink, the desktop entry, metainfo and hicolor icons) is in `lib.sh`. The clean-machine tests are in `native/packaging/test/linux/`.

| Script | Arguments | Writes |
|---|---|---|
| `../build/linux.sh` | `<repository> <arch> <out>`, with `MCBENCH_DATA_BUNDLE` (and `MCBENCH_SWIFTSHADER_CACHE`) | the payload folder: `mcbench-lite`, `mcbench-build-child`, `mcbench-sandbox-agent`, and on x86_64 `libvk_swiftshader.so` and `licenses/swiftshader/` |
| `../build/swiftshader.sh` | `<cache> <out>`, on x86_64 | `libvk_swiftshader.so` and `licenses/swiftshader/` in `<out>`, refused unless the driver's sha256 is the pin's (`linux.sh` runs it) |
| `archive.sh` | `<payload> <version> <arch> <out>` | `mcbench-lite-linux-<arch>.tar.gz` (install-source `script`) |
| `deb.sh` | the same, with `MCBENCH_LITE_SIGNING_KEY` | `mcbench-lite_<amd64\|arm64>.deb` (install-source `apt`) |
| `rpm.sh` | the same, with `MCBENCH_LITE_SIGNING_KEY` | `mcbench-lite.<arch>.rpm`, signed (install-source `dnf`) |
| `appimage.sh` | the same, on an `<arch>` machine | `mcbench-lite-<arch>.AppImage` (install-source `appimage`) |
| `aur.sh` | `<release folder> <version> <out> <arch>...` | `PKGBUILD` and `.SRCINFO` of `mcbench-lite-bin` (install-source `aur`), for the archives of the named architectures in the release folder |
| `apt-repo.sh` | `<release folder>`, with `MCBENCH_LITE_SIGNING_KEY` | `Packages`, `Release`, `InRelease`, `Release.gpg` among the release's assets |
| `dnf-repo.sh` | `<release folder> <version> <site folder>`, with `MCBENCH_LITE_SIGNING_KEY` | `<site>/rpm/repodata/`, `repomd.xml` signed, naming the packages in the release `v<version>` |

`MCBENCH_LITE_SIGNING_KEY` names the armoured OpenPGP secret key of the apt and dnf repositories (the owner's; a test makes a staging one with `test/linux/staging-key.sh`). The packages carry its public part. `MCBENCH_LITE_RELEASES` (default `https://github.com/adonis-singh/mcbench-lite/releases/latest/download`) and `MCBENCH_LITE_SITE` (default `https://adonis-singh.github.io/mcbench-lite`) are the two addresses the packages name: the `.deb`'s apt source is `$MCBENCH_LITE_RELEASES/` with `Suites: ./`, the `.rpm`'s repo file is `$MCBENCH_LITE_SITE/rpm/`, and the dnf metadata and the PKGBUILD name the files of the release `v<version>` under `$MCBENCH_LITE_RELEASES` with `latest/download` replaced by `download/v<version>`. The release tag is therefore `v<version>`.

The archive, the `.deb` and the AppImage are the same bytes each time from the same payload (checked twice on adipc). The `.rpm` is not, because its signature records the time it was made; the repositories' files record the time too.

## The build's image

The release build runs in Debian 10 "buster" (`debian:buster`, by digest), the image `scripts/release-engine.js` builds the engine in, with its packages from archive.debian.org (frozen). The whole workspace builds there: the window toolkit's headers (xcb 1.13, xkbcommon 0.8.2, wayland 1.16, freetype 2.9.1, fontconfig 2.13.1), gcc 8 for the C code (`ring`, the bundled SQLite) and V8's prebuilt static library all link against glibc 2.28, so nothing forced a newer base. Rust 1.99.1 is installed in the container by rustup-init 1.29.3 (sha256 as `server/tools.js` pins it) into the build's work folder. A cold build of all three programs took 435 s and 450 s on adipc in a 4-CPU container (2026-11-17, load average 9 to 17 from other work; indicative).

## The software Vulkan driver

On x86_64 the payload folder holds SwiftShader's Vulkan driver `libvk_swiftshader.so` and, in `licenses/swiftshader/`, the licences of everything compiled into it: SwiftShader's `LICENSE.txt`, and those of marl, SPIRV-Tools, SPIRV-Headers, Subzero and LLVM as Subzero carries it, each named by its path in SwiftShader's tree with `/` turned into `-`. The app's renderer opens the driver itself, without the Vulkan loader, when the machine has no GPU adapter; the path it is given is `<folder of the program>/libvk_swiftshader.so`. aarch64 has no driver, because it needs SwiftShader's LLVM reactor built on an arm64 machine, which has never been built.

`../build/swiftshader.sh <cache> <out>` builds it by the recipe and pin of `scripts/release-draw.js` (FLOOR, buildFloor; `native/draw-floor/README.md`), which give the helper's release the same bytes: SwiftShader at commit `f9d5d49a3c599a315e3493dc1e9b5309cffb3305` fetched from `https://swiftshader.googlesource.com/SwiftShader`, built in `almalinux:8` by digest (glibc 2.28) with gcc-toolset-13, the Subzero reactor, libstdc++ and libgcc linked in and a non-executable stack, stripped in the same container, and refused unless its sha256 is `1637fb0f1a642dd99b9c857e4355144239c8a3e7d7742c08da6498e7f71dbe8b` and its size 4,613,672 bytes. `<cache>` keeps the fetched source and the checked driver with its licences; a later run copies the cached driver when its sha256 is the pin's and builds nothing. `../build/linux.sh` runs it after the programs' build with `MCBENCH_SWIFTSHADER_CACHE` as the cache (default `<work>/swiftshader`). On adipc at two CPUs (2026-11-18, load 17 to 33), a run from an empty cache took 260 s, 252 s of it the container, and a second run that reused the fetched source took 189 s; both gave the pinned bytes, and a run from the cached driver takes under a second. The source fetched at that commit is 1.4 GB.

Every route installs the driver with the payload: `install_payload` in `lib.sh` (archive, `.deb`, `.rpm`, AppImage) and the `PKGBUILD`'s `package()` copy it into the payload folder with mode 644 and the licences beside it, on x86_64 only. The packages remove it by their file lists (`apt purge`, `dnf remove`, `pacman -Rns`); `install.sh --uninstall` removes the payload folder whole, and the in-app updater swaps the payload folder whole. It names `libdl.so.2`, `libpthread.so.0`, `librt.so.1`, `libm.so.6`, `libc.so.6` and `ld-linux-x86-64.so.2` and needs glibc 2.27 symbols at most, so the packages name no dependency for it. The `.rpm`'s spec excludes `/usr/lib/mcbench-lite/` from rpm's generated `Provides`: without that, rpm announced `libvk_swiftshader.so()(64bit)` as a library the package offers to others. The `.deb`'s AppArmor profile allows every file to be read and mapped executable (`allow file rwlkm /{**,}`), so the driver's path needs no rule of its own.

The x86_64 payload of a real `../build/linux.sh` run (2026-11-18, 1,360 s at two CPUs with the profile step, the driver taken from the cache) was packaged by each route and installed in a fresh container of each system: Debian 12, Debian 13 and Ubuntu 24.04 by `apt install` of the `.deb`, Fedora by `dnf install` of the `.rpm`, Arch by `makepkg --nodeps` of the generated `PKGBUILD` and `pacman -U` (which installs the dependencies), Debian 13 by `install.sh` from the archive, and Debian 13 by `--appimage-extract` of the AppImage. In each, the installed driver had the pinned sha256 and mode 644, `ldd` found every library it names, and a direct load without the loader (a small C program: `dlopen`, `vk_icdGetInstanceProcAddr`, `vkCreateInstance`, `vkEnumeratePhysicalDevices`) listed one device, `SwiftShader Device (Subzero)`. After `apt purge`, `dnf remove`, `pacman -Rns` and `install.sh --uninstall` the payload folder, the driver and `licenses/swiftshader/` were gone. The helper `mcbench-draw` of the draw release 7b3c1fd853233020, given `--software-vulkan` with the payload's driver, drew its synthetic pack's five pictures in a `debian:13` container with no `/dev/dri` and no graphics library, byte for byte the pictures it draws with its own release's driver.

## Ubuntu's AppArmor and bubblewrap

Ubuntu 24.04 and later set `kernel.apparmor_restrict_unprivileged_userns=1`: a program without an AppArmor profile that allows `userns` may create a user namespace, but is then moved into the profile `unprivileged_userns` (`/etc/apparmor.d/unprivileged_userns` in the `apparmor` package), which denies every capability in it, so bubblewrap cannot set up its mounts. What each release ships, read from the packages themselves on 2026-11-17:

| Release | `apparmor` package | Profile for `/usr/bin/bwrap` loaded by default |
|---|---|---|
| Ubuntu 24.04 | 4.0.1really4.0.1-0ubuntu0.24.04.9 | none: `bwrap-userns-restrict` is only in `apparmor-profiles` as `/usr/share/apparmor/extra-profiles/bwrap-userns-restrict`, not loaded |
| Ubuntu 26.04 | 5.0.2-0ubuntu1~26.04.1 | `/etc/apparmor.d/bwrap-userns-restrict`: `bwrap` may create namespaces with capabilities, and everything it runs is in `unpriv_bwrap`, which denies every capability |

Both were tried on Ubuntu's own cloud images in a VM (`test/linux/ubuntu-vm.sh`, 2026-11-17): Ubuntu 24.04.5 with kernel 6.8.0-147 and Ubuntu 26.04.1 with kernel 7.0.0-43, bubblewrap 0.9.0-1ubuntu0.3 and 0.11.1-1ubuntu0.3 from `apt install`. The tests are `mcbench-sandbox`'s `linux_box` (8 tests, the networked box among them) and `network` (2 tests, the refused-range matrix and the undo attempts), run as an ordinary user against the installed programs, and `mcbench-lite headless turn` making a `bash`, a networked `bash` and a `build` call. The rows with the sysctl and with `bwrap-userns-restrict` on 24.04 were run by hand in the same VMs (the `unprofiled` way of the script).

| What runs the boxes | Ubuntu 24.04 | Ubuntu 26.04 |
|---|---|---|
| A program no profile covers (the `install.sh` and AppImage routes, and the `.deb` before this profile) | nothing starts: `bwrap: setting up uid map: Permission denied`, and `bash` answers the approved user-namespace sentence; `build` fails too, with `Error: Program process exited unexpectedly: bwrap: loopback: Failed RTM_NEWADDR: Operation not permitted` (the build child's bubblewrap, in `unprivileged_userns`) | `bash` and `build` work; the networked command fails: `iptables v1.8.11 (nf_tables): Could not fetch rule set generation id: Permission denied (you must be root)`, then `mcbench sandbox keeper: the egress rules: iptables exited with exit status: 4`, because `iptables` runs under `/usr/bin/bwrap` and is in `unpriv_bwrap` (`apparmor="DENIED" operation="capable" profile="unpriv_bwrap" comm="iptables" capname="net_admin"`) |
| The same, after `sudo sysctl kernel.apparmor_restrict_unprivileged_userns=0` | everything passes | the same failure of the networked command: `bwrap-userns-restrict` applies whatever the sysctl says |
| The same, with `apparmor-profiles`' `bwrap-userns-restrict` loaded, as VS Code's issue advises (26.04 loads it by default) | the persistent box works and the networked command fails, as on 26.04 | the first row |
| A profile for the app's programs with only `userns,` in `flags=(unconfined)` (Ubuntu's own form for flatpak, VS Code and Bazel's `linux-sandbox` on both releases) | everything passes | as with no profile: an unconfined-mode profile's exec rules are not applied, so `bwrap` still takes the system's `bwrap` profile |
| The `.deb`'s profile, `apparmor/mcbench-lite` | everything passes | everything passes |

`apparmor/mcbench-lite` is a profile for `/usr/lib/mcbench-lite/mcbench-lite` and `/usr/lib/mcbench-lite/mcbench-sandbox-agent` in enforce mode that allows every kind of access, as unconfined does, `userns` among them. Its rules are those of 26.04's own `bwrap` profile, with two exec rules in place of that profile's move of every child into `unpriv_bwrap`: `/usr/bin/bwrap ix` keeps bubblewrap in this profile, and `pix /**` gives every other program the profile that attaches to it, or this one. Without the `ix` rule 26.04 fails as with no profile (tried). Nothing of the system's changes: the files under `/etc/apparmor.d` and the loaded profiles, the app's aside, are the same before the install, after it and after `apt purge`, which unloads and removes the app's profile.

The `.deb` holds the profile as `/usr/share/mcbench-lite/apparmor/mcbench-lite`. Its postinst copies it to `/etc/apparmor.d/mcbench-lite` and loads it with `apparmor_parser -r -T -W` only where `/proc/sys/kernel/apparmor_restrict_unprivileged_userns` reads 1 and `apparmor_parser` is installed; its prerm, on removal, unloads it and deletes the copy. The file is not in `/etc/apparmor.d` itself because the same `.deb` installs on Debian 12, whose AppArmor 3.0.8 cannot read it (`Could not open 'abi/4.0'`), where a file in `/etc/apparmor.d` would make every load of that folder fail; Debian 13's 4.1.0 reads it, and Debian's kernels do not restrict user namespaces, so the postinst does nothing on either. Installed and purged in `debian:13` with and without the `apparmor` package, the install and the purge exit 0 and leave no file; on Debian's 13 cloud image in a VM (kernel 6.12.117, AppArmor 4.1.0 enabled with 106 profiles loaded) the postinst installed no profile and the installed app's `bash`, networked `bash` and `build` calls passed. No package of 24.04 or 26.04 (their `Contents-amd64` of the release and `-updates` pockets) ships a file under `/etc/apparmor.d/mcbench*`, `/usr/share/mcbench-lite` or `/usr/lib/mcbench-lite`.

The `install.sh` route (`~/.local/lib/mcbench-lite`) and the AppImage (a path that changes on every start) run without root, so they cannot install a profile, and they stay as the first row says: on 24.04 a model and a person read the approved sentence, whose first remedy (the sysctl) makes everything work there and whose second (a profile for bwrap, which is what 24.04's `apparmor-profiles` offers) leaves the networked command failing as on 26.04; on 26.04 the `bash` shell works and the networked command answers with the `iptables` text above, which neither the approved sentence nor any other names, and neither remedy the sentence gives makes it work. The sentence's own check, `bwrap --unshare-user true`, fails on every system tried, including where bubblewrap works (`bwrap: execvp true: No such file or directory`, as nothing is bound into the new root). What a user of those routes would have to do on 26.04 is install the `.deb`, or, as root, load a profile like `apparmor/mcbench-lite` attached to their own copy's path (not tried).

Since 2026-11-18 the networked command needs neither. netinit, pasta's child, is unconfined there with every capability in pasta's user namespace, and now sets the rules itself, not under `/usr/bin/bwrap` (`native/crates/sandbox/src/linux/keeper.rs`, `run_rules`): with no profile, `bash`, the networked `bash` and `build` pass, and `linux_box` 9 of 9 and `network` 3 of 3 pass, on 24.04 at sysctl 0, on 24.04 with `bwrap-userns-restrict`, on 26.04 at either sysctl and on Arch. A box's init in `unpriv_bwrap` does not get bubblewrap's `--die-with-parent` signal (`bwrap --unshare-user --unshare-pid --die-with-parent --as-pid-1 --ro-bind / / sleep 777` outlives its killed parent on 26.04, and does not on Arch), so a box ends when its keeper's control socket reaches the end, which the app's side closes and which the kernel closes when the app dies. On 24.04 at sysctl 1 without a profile for bwrap nothing changed: the approved user-namespace sentence. pasta's "Can't run AVX2 build, using non-AVX2 version: No such file or directory" is pasta looking for `pasta.avx2` beside itself on a processor with AVX2; `native/crates/sandbox/rootfs/build.sh` now ships it from passt's own `make static` (whose `passt` is byte for byte the pinned rootfs's `pasta`), and a rootfs with it passed `linux_box` 8 of 8 and `network` 2 of 2 on 26.04 (before the two changes above, with the `.deb`'s profile attached to the tests' agent) and pasta printed no such line; the pinned asset has none until it is rebuilt.

Since 2026-11-20 `install.sh` on Ubuntu 23.10 and later, where the sysctl is 1 and no profile named `bwrap` is loaded (read from `/sys/kernel/security/apparmor/policy/profiles/*/name`, which every user may read), says why and asks once on the terminal whether to install Ubuntu's own `bwrap-userns-restrict` with sudo: the file from the installed `apparmor-profiles`, or else from that package fetched with `apt-get download` and unpacked, copied to `/etc/apparmor.d` and loaded with `apparmor_parser -r`. On 24.04 that adds only the profiles `bwrap` and `unpriv_bwrap`, and the route's `bash`, networked `bash` and `build` pass. No, no terminal or a failure leaves the install as before and prints the command that does the same later (not `apt install apparmor-profiles`, which also puts its 21 other profiles into `/etc/apparmor.d`). `--uninstall` keeps the file, which other programs using bubblewrap may rely on, and prints how to remove it. A profile for the install's own path in the home folder was rejected: the user can write there, and with it `unshare -Ur` became root.

Since 2026-11-20 the user-namespace sentence (`USERNS_MISSING`, in `native/crates/build/src/sandbox/linux.rs`) names Ubuntu's own profile first and `build` answers it too, in place of `Error: Program process exited unexpectedly: bwrap: loopback: Failed RTM_NEWADDR: Operation not permitted`. Its Ubuntu commands take `bwrap-userns-restrict` out of 24.04's `apparmor-profiles` without installing the package (`apt-get download`, `dpkg -x`), because `apt install apparmor-profiles` also installs and loads 25 other profiles in enforce mode (ping, traceroute, dnsmasq, avahi-daemon, nscd, samba's and syslog's among them; tried); then they copy it to `/etc/apparmor.d/` and load it with `apparmor_parser -r`. Its check is `bwrap --unshare-user --unshare-net --ro-bind / / true`, which fails at sysctl 1 without a profile (`bwrap: loopback: Failed RTM_NEWADDR: Operation not permitted`) and exits 0 with the profile or at sysctl 0; the old check, `bwrap --unshare-user true`, fails everywhere because nothing is bound into the new root. On 24.04.5 (the `install.sh` layout, a build that takes the pinned rootfs from `MCBENCH_SANDBOX_ROOTFS`): before, `bash`, the networked `bash` and `build` answer the sentence; after its four commands, run as the sentence wrote them, the check exits 0 and all three pass, and the files under `/etc/apparmor.d` and the loaded profiles are the same as before but for `bwrap-userns-restrict` and its two profiles `bwrap` and `unpriv_bwrap`; with that profile removed again and the sentence's sysctl instead, all three pass too. On 26.04.1 the sentence does not appear: its `apparmor` package already ships and loads `/etc/apparmor.d/bwrap-userns-restrict`, the check exits 0 and `bash`, the networked `bash` (no `iptables` error with `run_rules`) and `build` pass with no change; its `apparmor-profiles` (5.0.2) no longer holds the file, so the sentence's `cp` fails there, and its `apparmor_parser -r` reloads the system's own copy, after which all three still pass.

Not proven: a Debian 12 machine with AppArmor enabled (only the parser's refusal of the profile was seen, in a container); Ubuntu releases other than these two; the app's window, which these tests do not open. Sources: the profiles in Ubuntu's `apparmor` packages above, read in the VMs (`unprivileged_userns`, `bwrap-userns-restrict`, `flatpak`, `code`, `linux-sandbox`, `podman`); AppArmor's wiki page "unprivileged_userns_restriction" (gitlab.com/apparmor/apparmor/-/wikis/unprivileged_userns_restriction), for the default profile and the unconfined-mode semantics; Ubuntu's "Ubuntu 23.10: restricted unprivileged user namespaces" (ubuntu.com/blog/ubuntu-23-10-restricted-unprivileged-user-namespaces), for the per-application `userns` profile; Ubuntu's "Understanding AppArmor User Namespace Restriction" (discourse.ubuntu.com/t/58007); microsoft/vscode issue 316046, whose fix (pull request 320866) asks the user to repair bubblewrap rather than shipping a profile.

## The clean-machine tests

`native/packaging/test/linux/` reruns them on any Linux machine with Docker, from two payload folders built with `../build/linux.sh`, A and B (B from a scratch copy of the tree after `../set-version.sh`), both with `MCBENCH_UPDATE_KEY_FILE` the staging `minisign.pub` and `MCBENCH_UPDATE_FEED=http://mcbn-s5-linux-serve:8000/releases/latest/download/latest.json`:

```
export MCBENCH_LITE_SIGNING_KEY=<staging OpenPGP secret key, armoured> GNUPGHOME=<a GnuPG home holding it>
export MCBENCH_REPO_KEY=<its fingerprint> MCBENCH_SIGNING_KEY_FILE=<staging minisign.key> PATH=<folder of mcbench-feed>:$PATH
native/packaging/test/linux/stage.sh <payload A> <A> <staging>
native/packaging/test/linux/stage.sh <payload B> <B> <staging>
native/packaging/test/linux/tamper.sh <staging> <A> <B>
native/packaging/test/linux/serve.sh start <staging>
native/packaging/test/linux/machine.sh debian-12 apt <staging> <A> <B> <results>
native/packaging/test/linux/machine.sh fedora dnf <staging> <A> <B> <results>
native/packaging/test/linux/machine.sh arch aur <staging> <A> <results>
native/packaging/test/linux/machine.sh debian-13 apt-bare <staging> <A> <results>
native/packaging/test/linux/machine.sh debian-13 script <staging> <A> <results>
native/packaging/test/linux/machine.sh debian-13 appimage <staging> <A> <results>
native/packaging/test/linux/update.sh debian-13 script <staging> <A> <B> <sha256 of B's mcbench-lite> <results>
native/packaging/test/linux/update.sh debian-13 appimage <staging> <A> <B> <sha256 of B's mcbench-lite> <results>
native/packaging/test/linux/serve.sh stop
```

On a machine with a desktop session, run `stage.sh` inside `bwrap --dev-bind / / --tmpfs /run/user/1000 --unshare-pid --die-with-parent` so gpg's agent keeps its sockets out of the session's runtime folder (`../README.md`, A staging release).

`stage.sh` packages a payload with the staging server's addresses (`mcbn-s5-linux-serve` on the Docker network `mcbn-s5-linux-net`, no port on the host) and assembles it with `../release.sh --only linux-<arch>`, as a release is made. `server.py` answers as GitHub's releases and Pages do (two redirects for a `latest/download` link), and `serve_version` (`env.sh`) chooses which staged version's release and site it serves. `machine.sh` says in its header what each of its two containers does; `apt-bare` is apt without recommended packages, a system with no fonts and no fontconfig. The upgrade there is the system's own (`apt upgrade`, `dnf upgrade`). `update.sh` tests the in-app updater of the `script` and AppImage routes: A offered, then B (download, swap at the next start, `<name>.old` removed), the four refusals `tamper.sh` makes (an asset with one byte changed, a `latest.json` whose sha256 values were changed, a `latest.json` for an older version, a release signed with another key), and B waiting while a `headless engine` of the install runs.

Every package writes `version` beside `install-source`, and the app compares it with its compiled-in version at every start of a self-updating install. A payload repackaged under a higher version is therefore a changed install on the `script` and AppImage routes, so their update tests need two real builds, one per version. The apt, dnf and AUR routes read no `version` file.
