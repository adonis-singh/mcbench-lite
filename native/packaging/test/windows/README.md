# Windows packaging tests in the VM

Windows on ARM is not built: the first release has one Windows installer, `mcbench-lite-setup-x64.exe`, and one updater archive, `mcbench-lite-windows-x86_64.tar.gz`.

These scripts run on adipc against the Windows 11 VM (`docs/native-app.md`, The Windows VM) in its hold slot. `hold.sh` has the take, boot, stop and release, in the VM owner's lines for the two slots (`native/tools/winvm/env.sh`); the other scripts and the guest steps in `guest/` do not depend on how the VM is held. Each run uses an overlay of its own, `~/mcbench-native-scratch/s5/win/run/`, on the never-written base `win11-tools`, and one trap stops the VM, deletes the overlay and releases the hold slot's LOCK on every exit; a hold is that LOCK only, since the slot's pinned threads are outside the shared pool. Bring the tree to adipc by content first (COMMON's `git ls-files ... | rsync -rlp --checksum` line) and run the scripts from that copy.

## A fast loop for one crate: `vm-cargo.sh`

`vm-cargo.sh <tree> <log folder> -- <cargo arguments...>` runs one cargo command of the native workspace in the VM's hold slot as `bench`, for example `vm-cargo.sh tree logs -- test -p mcbench-updater --all-features --locked --no-fail-fast`, where the whole of `native/check.sh --windows` would take over half an hour and stop at the first failing crate. The tree goes into the guest by content as the check's does (a file whose bytes differ is written with the time now, identical files keep their times, files not in the tree go), into `\ctree` on stage five's own cache disk `~/mcbench-native-scratch/s5/win/cache.qcow2`, which also keeps cargo's registry (`\cargo`) and the target folder (`\ctarget`), so a second run is incremental; the check's cache disk is never attached. cargo runs from `native\` with the toolchain of `native\rust-toolchain.toml`, 4 jobs and 4 test threads, `CARGO_INCREMENTAL=0` and no debug information. Its whole output goes to `<log folder>/cargo-<time>.log` whether it passes or fails, and the script's exit status is cargo's.

## How the scripts reach the guest

Commands run over ssh through env.sh's `ssh_opts` (the hold slot's port 3156) as `bench`, the administrator that is logged on at boot, or `plain`, the standard user (members of Users only); both accounts take the same key. PowerShell is the ssh shell. An ssh session has no desktop, so a step that needs `plain`'s desktop (`window`, `wsl-screen`, `quit`) runs as a one-shot scheduled task with an Interactive principal for `plain`, started by `bench` (the same mechanism as the winvm scripts' `guest/gui.ps1`, which runs in `bench`'s desktop). For those, `vm-test.sh` first makes `plain` the account Windows logs on at boot (the Winlogon values in the overlay only, with the VM's one generated password from `winvm/vm/creds.txt`, sent on ssh's standard input and never printed) and reboots.

A screenshot is QEMU's `screendump` through the slot's QMP socket: env.sh's `qmp` function runs the installed `winvm/scripts/qmp.py` (`qmp.py <socket> screendump <out.png>`), which is what the winvm scripts' `screenshot.sh` does. It shows the desktop of the account logged on at the VM's display: `bench` in `vm-standin.sh`, `plain` in `vm-test.sh`.

## The comparison of the profile and HKCU

`listing` writes every path under `%USERPROFILE%` and every key path of `HKCU` (from `reg export`); `compare` classes every path that differs between two listings, prints those whose path holds `mcbench` (in any case) with their class and a count of the others by class, and writes every line to `compare-full.txt`. A path left after uninstall under `%LOCALAPPDATA%\mcbench-lite` is the data folder; one under a place in `$WindowsOwn` (in `guest/vm-test.ps1`) is Windows' own; any other path left fails the run. `$WindowsOwn` holds the places Windows' logon, Explorer, PowerShell, the print spooler, the URL security manager, Direct3D and the Start menu (its `TileProperties` keys, which name a program launched from it) write for any program, and NSIS's uninstaller copy in `%TEMP%` is its own class. The "before" listing is taken once two listings 60 s apart are equal outside Windows' own places (a digest ends each listing's line), for at most 10 minutes, since `plain`'s first logon keeps writing its profile for minutes.

The stand-in run of 2026-11-17 (`vm-standin.sh`, before the uninstaller removed the empty `%LOCALAPPDATA%\Programs` and the empty `Uninstall` key) left, after two installs and uninstalls by `plain`: the data folder; Explorer's `Caches` and PowerShell's module cache under `AppData\Local\Microsoft\Windows`; `AppData\Local\Temp\~nsu1.tmp\Un.exe`, the uninstaller's copy of itself, which NSIS cannot delete while it runs from it; the empty `AppData\Local\Programs` and the empty `HKCU\...\CurrentVersion\Uninstall`, which the uninstaller now removes when empty; and the keys `Windows NT\CurrentVersion\Devices`, `PrinterPorts` and `Internet Settings\Lockdown_Zones`, `ZoneMap` and `Zones` with their subkeys, which Windows makes for a user's session.

## What a self-update must show

After a self-update the app itself sets `DisplayVersion` in the uninstall entry, so Windows' installed-apps list shows the new version (the updater's `apps_entry.rs`). What the app does (`native/crates/updater/LATEST.md`): at each start its updater's thread asks the feed for `latest.json`, and for a newer version downloads and verifies it within seconds and leaves it waiting beside the payload folder as `.mcbench-lite.update` and `.mcbench-lite.update.json`; the next start swaps it in before the core and runs the new program, whose core then removes the `.old` entries and writes `DisplayVersion`. A refusal is written to `update.log` once and remembered beside the install by the sha256 of the `latest.json` bytes that led to it. No step needs a control to press. `vm-test.sh` serves the feed from a folder of its own and changes what it offers between the steps. One run shows, in this order:

| What | How |
|---|---|
| With the feed offering A, a start downloads nothing | the feed serves B's `latest.json` with A's version (the app reads nothing after a version equal to its own); the first start asks for `latest.json` only, the payload is A's and reads A's version, nothing waits beside it, and `update.log` has no new line |
| A `latest.json` with a changed value is refused | the entry's size is one more than the signed one; a start refuses it before any download ("does not match its signed comment" in `update.log`), and A stays whole |
| An archive with a changed byte is refused | one byte of B's archive is flipped, served with B's `latest.json` re-serialized (the same content in other bytes, so the refusal is not remembered for B's own `latest.json`); a start downloads it and refuses it ("it is not the released file" in `update.log`), and A stays whole with nothing waiting |
| A copy of the app in another folder, marked `direct`, updates itself and leaves the installer's entry alone | the feed now offers B; `copy-direct` copies the installed payload of A to `C:\mcb\copy\mcbench-lite` with `install-source` `direct`; it is started, `.mcbench-lite.update` and `.mcbench-lite.update.json` appear in `C:\mcb\copy`, its window is closed and it is started again; its payload is then B's, it runs from that folder, no `.old` entry is left, and `DisplayVersion` is still the one the installer wrote. It shares the installed app's data folder and never runs beside it |
| The installed app updates itself | a start with the feed offering B leaves `.mcbench-lite.update` and `.mcbench-lite.update.json` in `%LOCALAPPDATA%\Programs` (waited for up to 120 s); the window is closed and the app is started again, which swaps; the installed payload is then B's, its `version` file reads B's version, and the running program is `%LOCALAPPDATA%\Programs\mcbench-lite\mcbench-lite.exe` with B's sha256 |
| `DisplayVersion` follows | it reads B's version, waited for up to 60 s: the new program writes it once its core runs |
| The previous version is removed | no `.old` entry is left in the payload folder (waited for up to 60 s) and no `.mcbench-lite.update*` entry beside it; `update.log` has no new line |
| `MCBENCH_UI_LOG` | the updated app writes JSON lines with its `renderer` and `fonts` lines (and `first_frame` in builds that write it) |

Before every screenshot of the app's window the guest presses Escape while another program has the keyboard focus (the Start menu) and gives the app's window the focus. Before every start the guest prints what the data folder's `server.pid` holds, and after every quit whether it is still there: the app leaves it behind on Windows, and a start refuses while another live process has that pid, showing the fatal screen ("mcbench-lite — stopped"). When that happens the run keeps the screen and the file's content, then deletes the stale `server.pid`, says so, and starts once more.

The app has no command that prints its version, so "the running program's version" is read as the running program's path and its file's sha256, which must be B's `mcbench-lite.exe`.
