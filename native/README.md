# native/

The native app's Cargo workspace. The plan is `docs/native-app.md`; each crate's `lib.rs` (the binary's `main.rs`) opens with what crosses its seams, who owns each side, which of today's tests define it, which of today's modules it replaces, and what is still open and what settles it. Bodies are `todo!("stage N: ...")` until their stage builds them.

`core/` (the engine) and `renderer/` (the mesher) are not members and nothing here changes a file in them: their sources and lock files are hashed into the engine's and the mesher's released versions. Crates depend on them by path; `native/check.sh` fails if a build changes either folder.

## Crates and owners

Three sessions work from this branch in parallel: the stage-two session (the renderer; it also arbitrates seam disagreements and keeps `native-app` up to date with `main`), the stage-three session (the server ported to Rust) and the stage-four session (the interface).

## Changing a seam

A seam is a public type or trait of another owner's crate, or one both sides use (for example `mcbench_agent::TurnEvent`, which the interface shows, or `mcbench_ui::Command`, which the core handles). A change to one is proposed to its other owner by a message before it is committed; the stage-two session arbitrates when they disagree. Every trait has a seam test that writes a fake implementation of it, so a changed trait breaks a test on the side that did not change it.

## Merging into `native-app`

Each session works on its own branch cut from `native-app` and rebased on it. Before merging, `native/check.sh --jobs N --remote adipc` is green (both machines; `--jobs` 1 to 8 as the work needs, and `--slice mcbench-<session>.slice`, your session's slice in adipc's shared pool), and `--node` too when the change touches the Node app. The owning session merges with `--ff-only` or a merge commit.

How changes land on `native-app`, since 2026-11-17 at 22:54 (set by the main session to stop merges waiting hours behind the Windows half):

| Rule | What it says |
|---|---|
| Two halves gate | A merge into `native-app` needs the Mac and adipc halves green on the tip. The Windows half (`native/check.sh --windows-only`, which runs it alone and never waits for the Mac's turn) starts at once after the fast-forward and must be green within the hour. A Windows failure is fixed forward before anything else of that session's, or the merge is reverted. |
| Land small | One change per tip where it can be; whatever is green on two halves goes in when it is green. |
| Results carry over | When `native-app` moves under a session by commits that touch none of the files and crates its tip changes or depends on, the session merges and carries its results over, saying so in the merge message. Only the halves whose inputs changed are rerun. |
| A test that passes on a rerun | A test that fails once and passes on a rerun with no code change is marked ignored with its owner and reason in the same hour, listed under Known failures below, and fixed within the day; it does not hold a merge. |
| VM slots | The check slot is for merge checks; long Windows work uses the hold slot. |
| `main` | Unchanged: nothing goes to `main` without all three halves green on the same commit, and the stage-two session is its arbiter. | Nothing is force-pushed and nothing is pushed to any remote. When `main` moves, the stage-two session merges `main` into `native-app`.

## `native/check.sh`

```
native/check.sh --jobs N         fmt --check, clippy -D warnings, test, doc (warnings are errors), here; N is required, 1 to 8
native/check.sh --jobs N --remote adipc --slice mcbench-<session>.slice
                                 the same here and on adipc, both results printed; the adipc run is a systemd user
                                 scope in that slice under mcbench.slice, with no quota of its own; it fails at once
                                 when mcbench.slice has no CPUQuota or MemoryMax
native/check.sh --windows        also clippy -D warnings and test for x86_64-pc-windows-msvc in the Windows 11 VM on adipc
native/check.sh --windows-only   the Windows half alone, from the Mac or adipc, with no local half: it never waits for the Mac's turn
native/check.sh --node           also npm test in this checkout
native/check.sh --macos-vm       Mac only: also the bash sandbox's tests against the macOS VM
```

What a release build compiles is built by some half of the check (the main session's ruling of 2026-11-18, after the static sandbox agent stopped building with all halves green). Both halves run `cargo test -p mcbench-updater --features feed`. The adipc half also checks `mcbench-sandbox`'s library and programs for `x86_64-unknown-linux-musl` and `aarch64-unknown-linux-musl`, and checks `mcbench-lite --features shipped-data` against the data bundle `native/minecraft-data.lock` names. The check reads that bundle from `~/mcbench-native-scratch/check-toolchain/data-bundle/<its sha256>.tar.zst` on adipc, so a change to the lock puts the bundle `bundle.sh` wrote there in the same landing. The adipc half also builds the static sandbox agent for x86_64-unknown-linux-musl and, with it, the x86_64 root filesystem in `check-windows/assets` and Codex 0.169.0 as `install.rs` pins it (fetched once into `check-toolchain/codex-package`), runs `cargo test --workspace` with the variables the Codex box tests read, then `codex_box`, providers' `execute_only` and `linux_box` with `--ignored`; the Windows half runs `cli`'s `windows_codex_wsl` in the distro, with the package in its WSL files. Not built by any half, with the reason: the Intel Mac release (`x86_64-apple-darwin`) and ARM Linux (`aarch64-unknown-linux-gnu`), whose C build scripts need a cross toolchain neither machine has; the build child's release profile with its LTO link (the halves build it as debug); and the Linux release's Debian 10 container (glibc 2.28), whose older libraries only the release build meets. The release pipeline builds those, and a failure there is fixed before the release.

The Mac half fails when a crash report appeared while it ran (agreed with stage three, 2026-11-18): before the checks and after, it lists the names, and nothing more, in `~/Library/Logs/DiagnosticReports` and `~/Library/Application Support/CrashReporter` whose stem (the name before `-YYYY-MM-DD`, or before the first `_` in the second folder) matches `^(mcbench-.*|child-[0-9a-f]{16}|js-child-.*|rust-objcopy|.*-[0-9a-f]{16})$`, and names each new one; it reads and deletes none.

`--windows` builds with real MSVC in the Windows 11 VM on adipc (`native/spikes/winvm` on branch `claude/sharp-mendeleev-e55a37`, installed in `~/mcbench-native-scratch/winvm`), because the workspace has C code (the bundled SQLite of `rusqlite`, `ring`, V8's prebuilt static library) that a check from macOS or Linux cannot compile. Started on the Mac or on adipc, from a git checkout (from a tree without `.git` it fails at once saying so), it copies the files of `native/`, `core/`, `renderer/`, `server/` and `README.md` (the setup crate's tests read it) as git lists them to `adipc:~/mcbench-native-scratch/check-<branch>/windows-tree` and runs `native/check.sh --windows-vm` there from that copy, which runs in the VM's check slot and takes its `LOCK` (`~/mcbench-native-scratch/winvm/LOCK-check`: a slot has one user at a time) through `~/mcbench-native-scratch/winvm/scripts/lock.sh` (it waits up to an hour, printing the holder each time it changes, then fails quoting the holder's line and saying how to clear a stale `LOCK`; the check fails at once when the installed `lock.sh` is not the repository's `native/tools/winvm/lock.sh`), makes a fresh overlay of the base `win11-tools` for this run alone (`~/mcbench-native-scratch/check-windows/run`; the base is never written), boots the VM headless with the check's cache disk as a second drive, brings the tree kept on the cache disk (`\tree` beside its `\target`) to the run's tree by content and runs `cargo clippy --workspace --all-targets --locked -- -D warnings` and `cargo test --workspace --locked` of whatever workspace the tree holds, with the toolchain of `native/rust-toolchain.toml`, without debug information or incremental compilation (`CARGO_INCREMENTAL=0`, `CARGO_PROFILE_DEV_DEBUG=0`, `CARGO_PROFILE_TEST_DEBUG=0`, as the wrapper on adipc sets them: a check needs neither, and MSVC's PDB files fill the cache disk), and prints what the cache disk's registry, targets and tree take. The cache disk `~/mcbench-native-scratch/check-windows/cache.qcow2`, shared by every session's checks as `check-toolchain/` is (a sparse 40 GiB qcow2 holding one NTFS volume labelled `mcbcache`, made and formatted when missing; it takes on adipc only what the guest has written: 13 GB after a cold run of stage three's workspace at `bb59785b`, more with the interface's GPUI), holds only cargo's registry and the target folder, with V8's downloaded library (about 200 MB) and the built dependencies, so a rerun is incremental, as the target folder is on the Mac and on adipc; deleting it is always safe, and the next run then downloads and builds everything. It is kept between runs with a bound: when a run starts and the disk takes more than `MCBENCH_WINDOWS_CACHE_MAX_GB` on adipc (`qemu-img info`'s "disk size"; default 20), the run deletes it, prints `check: the cache disk held N GB, over 20: deleted, this run is cold`, and builds cold. The VM counts as four threads: QEMU runs pinned to the check slot's host threads 28-31 and the guest's cargo runs with min(N, 4) jobs and test threads; QEMU is found and stopped only by the pid file its start writes, never by a pattern. One trap stops the VM, deletes the run's overlay and the tree's `.tar` and `.ps1`, and releases the `LOCK` on every exit, failed or interrupted, so Windows itself starts clean every run.

The WSL tests (`check.sh`'s header, "The WSL tests"): the Windows half's check slot boots `winvm/vm/bases/win11-tools-wsl.qcow2` (with `win11-tools-wsl.vars.fd` and `win11-tools-wsl.tpm`), a qcow2 whose backing file is `win11-tools.qcow2` with WSL installed once and Windows restarted, made in the hold slot as the shared notes' `check-sh-wsl.md` ("Making win11-tools-wsl") says; `--windows` and `--windows-only` need `--slice`, because adipc first builds the guest's Linux files (`check.sh --wsl-assets`: the x86_64 guest base, the Linux build child, the escape probe) in a scope of that slice from `check-<branch>/tree`, brought by content, into `check-<branch>/wsl-assets`. They need the x86_64 root filesystem installed once in `~/mcbench-native-scratch/check-windows/assets` (`mcbench-sandbox-rootfs-amd64.tar.zst` and `.sha256`; 82,756,487 bytes, counted in stage three's disk budget), made with Docker on adipc by `MCBENCH_DOCKER_PREFIX=mcbn-s3- native/crates/sandbox/rootfs/build.sh <out> amd64` (its images and containers are named `mcbn-s3-*` and listed in `<out>/docker-names.txt`; remove them by name afterwards) and copied there under the hold slot's LOCK; the one installed is the pinned one, sha256 `786d552ac02865a6542f32605d6bfb47f2c5148b0f8ce78b27b7c4aa75fd955f` (`native/sandbox-assets.lock`'s x86_64 root filesystem). The base image and these files are shared: making or replacing them takes the hold slot's LOCK, as any VM work does.

Both kept targets, adipc's `check-<branch>/target` and the cache disk's, are fed by content and never by modification times, because cargo takes a path crate's build as fresh when the files are not newer than it, and a tree copied with its own older times over another branch's or a later commit's build would be compiled against that build's crates: with `--remote` the run's files go to `check-<branch>/stage` and `rsync -rlp --checksum --delete` (no `-t`) brings `check-<branch>/tree` to them; in the guest, for every file of the run's tar's own list, a kept file whose size or SHA-256 differs, or that is missing, is written with the time now, identical files keep their times and files not in the list are deleted. No target folder is inside a tree.

`--macos-vm` (on a Mac; elsewhere it fails saying so) also runs `cargo test -p mcbench-sandbox --test macos_vm --test linux_box --test network --test native_diff -- --ignored --test-threads 1` with `crates/sandbox/macos/run-signed.sh` as cargo's runner (an ad-hoc signature with the virtualization entitlement, which shows nothing and asks nothing). It needs `MCBENCH_SANDBOX_GUEST` and `MCBENCH_SANDBOX_GUEST_SHA256` (the guest base, `crates/sandbox/guest/build.sh`) and `MCBENCH_SANDBOX_ROOTFS` and `MCBENCH_SANDBOX_ROOTFS_SHA256` (the aarch64 root filesystem), and fails before building anything naming the one that is not set; it sets `MCBENCH_SANDBOX_NETWORK=1` (the network test reaches the internet) and `MCBENCH_SANDBOX_SCRATCH` (default `$MCBENCH_NATIVE_CHECK_HOME/sandbox-vm`, kept so the root filesystem is unpacked once). With `--remote adipc` the Windows part runs once, after both machines' checks, so the VM never builds beside adipc's own build. Windows on ARM (`aarch64-pc-windows-msvc`) is not checked here: the C build scripts need an ARM64 C toolchain (`ring` needs clang for it), which the VM does not have; the release pipeline's `windows-11-arm` runner builds and tests it.

It builds outside the repository: `MCBENCH_NATIVE_CHECK_HOME` (default `~/.cache/mcbench-native-check`) holds the pinned toolchain (`RUSTUP_HOME`), rustup and the registry (`CARGO_HOME`) and the target folders (`CARGO_TARGET_DIR`): on the Mac one shared `target-mac` (with `target-mac-build-child` and `target-mac-draw` beside it) for every session and branch, since one Mac half runs at a time under the Mac's turn and builds one tree: the tree under check is brought by content into `~/.cache/mcbench-native-check/mac-tree` (the same files and rsync as adipc's; a changed file always gets a new time, so cargo never takes another tree's build as fresh) and the Mac half builds there, while `npm test` runs in the checkout itself; deleted by `check.sh` at the start of a turn when the three hold more than 24 GB together; elsewhere one per branch. A session clears the Mac's target by hand only while it holds the Mac's turn, deleting the three folders; a session's own `target-<branch>` folders on the Mac are no longer used and are its to delete; each of the three is taken from the environment when set, and none may be in `~/.mcbench-lite/tools`. The tests' `TMPDIR` is always `$MCBENCH_NATIVE_CHECK_HOME/t/<cksum of the branch name>` (on adipc under `~/mcbench-native-scratch/check-toolchain/t/`; a short name of fixed length, because tests make Unix sockets under it and a socket's path must stay under 104 bytes on macOS and 108 on Linux), emptied at the start of each run and kept after it, so what a failed test left there can be read; no variable names it, because the script deletes it. The first run installs rustup-init 1.29.3 (checked against `server/tools.js`'s sha256) and the toolchain of `native/rust-toolchain.toml` (1.99.1, as `core/`) with clippy and rustfmt. On adipc the tree is brought by content to `~/mcbench-native-scratch/check-<branch>/tree`, builds into `check-<branch>/target` with `--jobs N` in a CPUQuota scope, and shares `~/mcbench-native-scratch/check-toolchain/`; delete a branch's `check-<branch>` folder when the branch is merged. `core/` prints its own compiler warnings while it builds; they are `core/`'s and do not fail the check. Format with `cargo fmt` in `native/` and never with `cargo fmt --all`, which also formats the path dependencies and so rewrites `core/`. It builds with `CARGO_INCREMENTAL=0` and `CARGO_PROFILE_DEV_DEBUG=line-tables-only` on both halves (the Windows guest with no debug information at all), so one cold target folder takes about 16 GB on adipc instead of the 54 GB of cargo's defaults.

## Decisions of stage three

Settled by the stage-three session on 2026-11-17 before it built anything; each crate's doc repeats its own under `Decided`.

| Question | Decision | Why |
|---|---|---|
| The async runtime | tokio, multi-thread, owned by the core and internal to stage three's crates. Their I/O traits (`Provider::complete`, `Tool::call`, `Sandbox::exec`, `BuildRunner::run`, `run_turn`, the bridge) are `async fn` behind `#[async_trait]`, cancelled by `tokio_util::sync::CancellationToken`. The engine, the world and SQLite run on dedicated threads or `spawn_blocking`, never on a runtime worker. `mcbench_render::Renderer` stays blocking (the tools call it through `spawn_blocking`), and `mcbench_ui::Core::send` and `Window::publish` stay synchronous, so GPUI's executor and tokio never meet. HTTP is `reqwest` on `rustls` | Cancellation and timeouts for provider streams and child processes without a thread each; Unix sockets and Windows named pipes for the tool bridge from one library |
| How Rust reads the text that reaches models | The text stays where it is in `server/` and no file there changes. `native/crates/agent/contract/` holds it as files generated mechanically from `server/`'s sources and output by a script kept beside them, never edited by hand, read with `include_str!`. Two tests hold it: the sha256 of `mcbench-lite headless contract` equals `efc4d688...` for the benchmark's 8 forms (always run), and with `--node` the script regenerates every file and every form (network, chat, resolution and budget variants included) is compared with Node's output byte for byte | Moving the text into shared data files would change files that hold model text on `main` for no gain; when Node is deleted at stage five the generated files become the only copy and the pinned hash still judges them |
| JSON a model or Node reads | A crate of its own, `mcbench-json`: `JSON.stringify`'s output from Rust (JavaScript's number-to-string, its key order for index-like keys, its escapes, the indented form), used wherever Rust writes JSON that today's JavaScript wrote | `serde_json` writes `2.0` where JavaScript writes `2`, and `1e21` where JavaScript writes `1e+21` |
| The typed message | Agreed with the stage-four session on 2026-11-17. The row's JSON text stays the source of truth, private to the store and never rewritten from a typed value; `mcbench_store::Message` is an enum by role decoded on load, read-only, with unknown fields refused; new rows come from one constructor per writer site of today's server, in that site's key order. `Update::Transcript` carries a header, `Vec<StoredMessage>` and the branch tree; a tool result is shown through one typed `ToolShown` for stored and streamed results, and a stored tool call carries the same summary line `ToolStart` does, both made by the core. What goes to providers stays an order-preserving JSON object inside stage three's crates | Today's server writes the same keys in two orders in two places, and key order reaches models (the context archive's file name is a hash of the stringified message), so one typed struct cannot be the stored form; the interface never builds or parses message JSON |
| The engine's panic rule and 1 GiB stack (`core/src/main.rs`) | Nothing under `core/` changes in stage three, so no engine release. `mcbench-lite headless engine` compiles `core/src/main.rs` itself with `include!` and runs its `serve()` on a 1 GiB thread, so the protocol loop is the released program's source. `mcbench-engine`'s typed binding repeats the two rules, held by a test that drives the same requests through both. `VERIFY` keeps its files in a scratch folder per call | A change to `core/` costs a public release and a new pin for no change in behaviour; the rules move into `core/`'s library when Node and the engine releases go at stage five |
| Cursor | Not built: the owner decided on 2026-11-17 to leave Cursor out of the native app for now (`docs/native-app.md`, Cursor, deferred). `ProviderId::Cursor` stays as a name stored chats carry; `Provider` stays open to a provider run as an external program | Cursor's CLI is about 600 MB unpacked per platform with no documented way to limit it to mcbench's tools, and its SDK needs Node |
| The engine's build | The workspace's release profile is `core/`'s (`lto`, one codegen unit). The profile in `core/pgo` matches nothing in a workspace build (cargo gives `mcbench_core` another crate hash there), so the release build uses the engine's pinned profile, recorded on the corpus and committed per target under `native/packaging/build/pgo/` (about 1.9 MB a target), for Apple silicon macOS, x86_64 Linux and Windows x64; Intel macOS and ARM Linux build with no profile (`native/packaging/build/pgo.md`). Until a build with such a profile is what ships, the private benchmark and the parity scripts drive the released engine program | Measured on adipc: in-process with a recorded profile meets or beats the released program on every row, without one it is 8 to 20% slower |
| Where `test_build` and settles run | In engine CHILD processes of the app's own binary (`mcbench-lite headless engine`, the released program's own protocol loop), kept warm in the pool as today's `engine-pool.js` keeps its subprocesses, killed on cancel, on the wall budget and when they die, with today's recovery. Only the live world of the open chat runs in-process. This corrects the plan's "settle pool in-process" | An in-process VERIFY or settle cannot be stopped: the verifier work showed a cancelled or over-budget run holds its lane until its ticks end (up to 72,000 ticks of dense content), and an engine that runs out of memory would end the whole app. A stop flag inside the engine would need a change under `core/`. A child process can be killed and its memory is its own, which is what today's app relies on; the cost is today's files-and-pipe protocol for those calls and about 25 ms to start a child, which the pool hides |
| The build child's program | Its own small program on all three platforms, `mcbench-build-child`, shipped beside the app; `mcbench-lite` has no `build-child` command. It is a workspace of its own, `native/build-child`, with its own `Cargo.lock`, because V8 146.9.0's `temporal_rs` compiles only against the icu_* crates at 2.1 while the window toolkit needs 2.3, and one lock cannot hold two 2.x versions of a crate; the app and the child meet only in the process protocol (`mcbench-build`'s seam). The Windows sandbox is built on `windows-sys` (already in the workspace), not `win32job` and the `windows` crate | On Windows a process that imports `user32.dll` cannot start with win32k system calls disabled, and the app links a window toolkit; everywhere the child then maps only V8 and the C runtime under its sandbox |
| What the app ships | macOS and Windows: two executables, `mcbench-lite` and `mcbench-build-child`. Linux: three, those two and the static musl `mcbench-sandbox-agent`, Codex's box relay and tool bridge. All in one folder; the app finds each beside its own executable, or by a variable for tests (`MCBENCH_BUILD_CHILD`, `MCBENCH_SANDBOX_AGENT_STATIC`) | On Linux Codex runs in its box on the model's shell's root filesystem, where the app's binary (glibc, the GPU libraries, V8) does not run |
| SQLite | `rusqlite` with the bundled SQLite (FTS5 and the JSON functions `server/store.js`'s SQL uses), one writer connection behind the store, a blocking API | The same SQL as today; a C dependency, which the Windows check must compile |
| The Windows build-program sandbox | The owner decided on 2026-11-17 on one attempt at wiring in Codex CLI's `windows-sandbox-rs` (`rust-v0.169.0`), and on the Linux build child inside the app's WSL2 distro if that stopped. It stopped at the crate's facts, before any wiring: its only backend that denies network needs an administrator's setup (two local user accounts, Windows Filtering Platform filters, firewall rules); the unelevated backend denies network only through proxy variables and does not limit child processes. Nothing of it landed; the Windows route is now the WSL2 distro | `docs/native-app.md`, The build-program sandbox |
| The data folder's lock | The native app takes today's localhost app's lock, `server.pid` in the data folder, by `server/pid-lock.js`'s steps (`mcbench_setup::instance`): a native app and today's server on one folder refuse each other, and each takes over a lock the other left when it died. `headless turn` takes no lock, as the benchmark's Node worker takes none on its per-attempt folder | With two different files both could run on one folder (`MCBENCH_DATA_DIR`), writing one SQLite database and each pruning the worlds against its own view |

Added by the `bash` sandbox's macOS work (2026-11-17):

| Question | Decision | Why |
|---|---|---|
| The `bash` box's limits on every platform | One mechanism, the keeper's (`mcbench-sandbox`, `linux/keeper.rs`): in a cgroup v2 folder delegated to it, a `box` cgroup with today's `memory.max`, `memory.swap.max`, `pids.max` and `cpu.max`. Only the delegation differs (`linux::Delegation`): a systemd user scope per box on a Linux host, the guest's init in the macOS VM and the WSL2 distro | A guest has no user systemd session, and rlimits cannot limit a box's memory as a whole or its CPU; the Linux host's path is unchanged |
| The macOS VM | Booted from Rust with `objc2-virtualization` 0.3.2 (no helper program): Debian 13's cloud kernel and a guest base of pinned Debian packages made by `crates/sandbox/guest/build.sh`, 2 vCPUs, 2 GiB, the sandbox folder and the root filesystem's folder by virtiofs, a sparse 8 GiB disk for the unpacked root filesystem, the NAT attachment, the agent over vsock; its clock kept on the host's through a virtiofs file | The bindings cover every class needed; Debian's kernel has virtiofs, ext4 and the console built in and the rest as modules, and snapshot.debian.org keeps every pinned file; the guest base's userland is also the WSL2 distro's |
| Who names the `bash` sandbox's files | Setup, in one function: `mcbench_setup::shell::files` hands the core the root filesystem and, on macOS and Windows, the guest base, each as a file and a sha256 (`ShellFiles`).
