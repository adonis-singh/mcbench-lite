# native/ci

Workflows kept as proposals: nothing runs a file in this folder. Enabling one is the owner's step: he copies it to `.github/workflows/` in the public repository `adonis-singh/mcbench-lite`. Each file opens with a comment saying what copying it does. Day-to-day checks run on the two local machines with `native/check.sh`; these workflows use GitHub's free standard runners, which the public repository has without limit.

| File | Started by | What it does | Secrets | Enabling it takes |
|---|---|---|---|---|
| `native.yml` | pull requests and pushes to `main` that touch `native/`, `core/` or `renderer/` | fmt, clippy, test and doc of the workspace and of the build child on the six runners | none | copying it |
| `release.yml` | a pushed tag `v*`, or by hand | builds, packages, tests and assembles a release with `native/packaging/release.sh` and ends with a draft GitHub release; it never publishes (`native/packaging/README.md`, A release, from tag to draft) | `MINISIGN_KEY`, `REPO_GPG_KEY` | the two secrets, `native/packaging/update-key.pub` committed, the sandbox assets' release published and its lock committed |
| `pages.yml` | a release being published, or by hand with a tag | deploys the `site` artifact of the release workflow's successful run for that tag to GitHub Pages | none | Pages set to deploy from GitHub Actions |
| `publish-aur.yml` | by hand only, with a published release's tag | pushes `PKGBUILD` and `.SRCINFO` from that run's `aur` artifact to `ssh://aur@aur.archlinux.org/mcbench-lite-bin.git`, after checking the AUR's Ed25519 host key against its published fingerprint | `AUR_SSH_KEY` | an AUR account and the secret |

`release.yml`'s jobs, in order: `version` (the tracked update key, the tag against the workspace's version, the sandbox lock published); `data` (the Minecraft data bundle regenerated with `native/tools/extract/regenerate.sh` on `ubuntu-24.04` with the pinned zstd 1.5.7 and Temurin 25.0.5+8, required to equal `native/minecraft-data.lock`, and `costab.sh`); `sandbox` (`sandbox-assets.sh check`); `feed` (`mcbench-feed`); `build-macos`, `build-linux`, `build-windows` on `macos-15`, `macos-15-intel`, `ubuntu-24.04`, `ubuntu-24.04-arm` and `windows-2025` (Windows on ARM is not in the first release); `package-linux`, `package-windows`; `rollback` (prints "not built yet" while `native/packaging/build/rollback.sh` does not exist, and does not hold back the release); `assemble`; `test-linux`, `test-windows`, `test-macos`; `draft`.

Every third-party action is pinned by its commit and the version is in a comment beside it. Each job has the least permission it needs: the workflow's default is `contents: read`, only `draft` has `contents: write`, and `pages.yml`'s deploy job has `pages: write` and `id-token: write`. No workflow runs on `pull_request_target`. A secret is passed in the environment of the one step that uses it, written to a file in the runner's temporary folder with mode 0600, unset, and the file is deleted when the step ends; no step prints one.

## A trial run

Before the first release, `release.yml` runs once with staging keys, from a branch made for it: the branch holds `release.yml` at `.github/workflows/release.yml` and the staging updater key's public half at `native/packaging/update-key.pub`, and nothing else differs from `native-app`. Trials 1 to 5 ran in the private repository `adonis-singh/mcbench-lite-dev` on 2026-11-19 and 2026-11-20. The next one runs in the public repository `adonis-singh/mcbench-lite`, on a branch beside an export of `native-app`; its `main` does not change. A tag `trial-<anything>` on that branch starts it. For such a tag the workflow skips three things a release needs and a trial cannot have: the tag need not equal the workspace's version, the sandbox assets' lock may still say `not-published-yet`, and the last job makes no draft release. Every other job runs as for a release, so the trial is the first build of Intel macOS and ARM Linux, the first rebuild of the guest bases on a GitHub runner against the lock, and the first signing with the secrets. Nothing is published, but a public repository's run is public: its logs, and its artifacts, which any signed-in GitHub user can download for 90 days. The artifacts are complete builds with the staging updater key, which would never take a real update, so they are deleted, with the run, as soon as its results are read. In a private repository the free plan's included minutes run out after about four runs, because macOS runners count tenfold; a public repository's standard runners cost nothing.

A private repository leaves ARM Linux out, trial or release. That was set while ARM Linux's build, having no pinned profile, first made an instrumented build: the `mcbench-lite` rustc of that build peaked at 10.6 GiB on x86_64 (adipc, 2026-11-19), a private repository's standard runners have 8 GB and a public repository's 16 GB, and in trials 3 and 4 the ARM job was killed for lack of memory, once with no swap and once with 16 GiB of swap. Since 2026-11-20 a target with no pinned profile builds with no profile, so ARM Linux makes no instrumented build (`native/packaging/build/pgo.md`, The three cases); its `mcbench-lite` rustc peaked at 4.5 GiB on x86_64 (adipc, 2026-11-20, 4 jobs). Whether ARM Linux's build fits a private repository's 8 GB runner has not been run, so the rule stays. The `version` job's `targets` step reads `github.event.repository.private`: in a private repository the `build-linux` and `package-linux` matrices hold x86_64 alone and `assemble` passes release.sh `--only` with the other four platforms; in a public one they hold both architectures and release.sh assembles every platform.

The two secrets for the trial are the staging keys of `native/packaging/test/linux/stage.sh` (adipc's `~/mcbench-native-scratch/s5/pipeline/staging/keys/`): `MINISIGN_KEY` is `minisign/minisign.key`, `REPO_GPG_KEY` is `repo-secret.asc`. They are throwaway keys; the real ones replace them in the public repository only.

## The winget pull request

The release's `winget` artifact (and `release/winget/` in the `release` artifact) holds the three manifest files of `adonis-singh.mcbench-lite` for that version, whose installer addresses are the versioned release assets. After publishing the release, the owner forks `microsoft/winget-pkgs`, adds the three files under `manifests/a/adonis-singh/mcbench-lite/<version>/`, checks them with `winget validate --manifest <that folder>` on a Windows machine, and opens the pull request. Microsoft's checks then install the package from the release; a reviewer merges it.
